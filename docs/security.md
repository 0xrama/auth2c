# Security

This document covers the authorization model, cryptographic invariants, browser threat model, and security limitations of Auth2C.

## Account-origin authorization model

Auth2C enforces a strict separation between relying-party apps and the account management UI:

- Every identity token carries a scalar audience of the form `origin:<normalized-origin>` (e.g., `origin:https://example.com`).
- The **account origin** is derived from `PUBLIC_URL` (e.g., `origin:https://auth.example.com`).
- Public endpoints (`/token`, `/session/check`, `/session/revoke`, `/auth2c.js`, discovery) use permissive CORS (`access-control-allow-origin: *`, non-credentialed).
- Account routes (`/account/overview`, `/account/grants`, `/account/sessions/revoke`, `/account/grants/revoke`) use same-origin CORS — the `access-control-allow-origin` header is set only if the request `Origin` equals the account origin.
- Bearer validation (`validateBearer`) requires an **active session row** keyed by the token's `jti`, an **active grant** for the session's `provider_sub`/`origin`, and the session's origin must match the token's audience origin.
- Account routes additionally require the session origin to equal the account origin. A valid third-party app token receives `403 insufficient_scope` rather than account-wide access.
- Account operations (session/grant revocation) are scoped by `provider_sub`, so cross-account IDs are indistinguishable from absent IDs.

## PKCE invariants

- PKCE S256 is **mandatory** — the `code_challenge_method` must be `"S256"`, the challenge must be at least 43 characters, and the code verifier must be at least 43 characters.
- The challenge is stored on the flow and code rows. At token exchange, `redeemCode` computes `SHA-256(verifier)` and matches it inside the atomic `DELETE ... WHERE challenge = ? RETURNING *`. A wrong or missing verifier yields zero rows and a uniform `invalid_grant` error — no information about which check failed is disclosed.
- The `code_verifier` minimum length (43 chars) is validated by `validateCodeVerifier` in `@auth2c/protocol`. Note: the worker's `tokenExchange` handler does not call `validateCodeVerifier` explicitly — the verifier is validated only implicitly via the SHA-256 hash match inside the D1 `DELETE` statement. This is secure because a short verifier produces a different hash than the stored challenge.

## State parameter and cookie handling

- The OAuth `state` parameter is a 24-byte base64url random token generated by the browser SDK.
- It is stored in `sessionStorage` (key `auth2c.transaction`) and set as the `a2c_flow` cookie on the `/authorize` response.
- The cookie is `HttpOnly`, `Secure`, `SameSite=Lax`, host-only, with `Max-Age=600` (10 minutes, matching `FLOW_TTL_MS`).
- At `/oauth/google/callback`, the URL `state` parameter must match the cookie value exactly. Mismatch throws an error.
- The flow is cleared on terminal success or failure via a `Set-Cookie` with `Max-Age=0`.

## OIDC nonce

- A fresh 18-byte random nonce is generated at `/authorize`, persisted on the flow row, and sent to Google as the `nonce` parameter.
- At callback, the Google ID token is verified with real `jose` `jwtVerify` against Google's JWKS, and the signed `nonce` claim must equal the persisted nonce.
- Nonce mismatch, signature failure, or claim failure is terminal — the claimed flow is deleted and the user must restart login.
- Pre-migration flows (created before `0003_security_hardening.sql`) have `nonce IS NULL` and are rejected as expired.

## Atomic callback and code redemption

- The callback uses an atomic claim: `UPDATE flows SET callback_claim_id = ? WHERE callback_claim_id IS NULL RETURNING *`. Exactly one concurrent callback can proceed.
- On transient Google transport failure, the claim is conditionally released so the browser may retry. On cryptographic/claim failure, the flow is deleted (terminal).
- Callback completion is a single D1 `batch` containing grant upsert/reactivation, code insertion, and claimed-flow deletion. No grant or code can survive partial completion.
- Code redemption uses a single linearizing statement: `DELETE FROM codes WHERE code_hash=? AND expires_at>? AND redirect_uri=? AND challenge=? RETURNING *`. The first caller wins; every subsequent caller (replay, wrong verifier, wrong redirect) gets zero rows.
- Session creation is conditional: `INSERT INTO sessions ... SELECT ... WHERE EXISTS (active grant) RETURNING id`. If the grant was revoked between code issuance and redemption, no session is created.

## Pairwise subject derivation

- Pairwise subjects are derived using HMAC-SHA256 keyed by `PAIRWISE_SECRET` over the input `provider_sub\0origin`.
- The output format is `pw_<base64url>`.
- The same Google identity produces a different `sub` for every relying-party origin. The raw `provider_sub` is never exposed outside the Auth2C database.
- Validation recomputes the expected pairwise subject from the session's stored `provider_sub` and origin; a token with a mismatched `sub` is rejected.

## Browser localStorage bearer token threat model

### How tokens are stored

The browser SDK stores the complete identity (including the raw JWT bearer token) in `localStorage` under the key `auth2c.identity`. The transaction record (verifier, state, redirect URI) is stored in `sessionStorage` under the key `auth2c.transaction`.

### XSS implications

Any successful cross-site scripting (XSS) attack on the relying-party app can read `localStorage` and exfiltrate the bearer token. This is an inherent limitation of browser-based bearer tokens.

**Mitigations**:

- Tokens are short-lived (15 minutes). Even if exfiltrated, the token expires quickly.
- Auth2C supports immediate session revocation via `/session/revoke`. If XSS is detected, the app can call `Auth2C.signOut()` which revokes the session server-side before clearing local state.
- However, `/session/revoke` requires the token itself — if the token is stolen, the attacker can also call `/session/revoke` (a denial-of-service on the session, but not on the grant).
- **Server-side revocation checking**: Relying parties should call the Auth2C `/session/check` endpoint (or Auth2C's `checkSession()` browser method) to verify that a token is still active before trusting its claims. A revoked or expired token returns `401` immediately.

### What `localStorage` means

- Tokens persist across browser tabs and browser restarts within the same origin.
- `sessionStorage` (used for the transaction) is per-tab and does not survive tab close — this is intentional, as the PKCE verifier must not persist beyond the callback.
- Clearing `localStorage` on the relying-party origin removes the identity but does **not** revoke the session server-side. Use `Auth2C.signOut()` instead.

## CSP and third-party-script guidance

### Current state

**The Auth2C hosted pages (including `/account`) do not set a Content-Security-Policy header.** The account page contains a large inline `<script>` and loads external resources (Google Fonts). This is a known gap.

### Recommendations for relying-party apps

Relying-party apps that embed Auth2C should:

1. **Set a strict CSP** on their own pages, including:
   ```
   script-src 'self' https://auth.example.com
   connect-src 'self' https://auth.example.com https://accounts.google.com
   ```
2. **Avoid inline scripts** on pages that handle Auth2C tokens, or use nonce-based CSP.
3. **Load `auth2c.js` from the Auth2C origin** (`https://auth.example.com/auth2c.js`) and pin its integrity with a `SRI` hash if desired.
4. **Do not store or process Auth2C tokens in server-rendered HTML** — tokens should only exist in JavaScript memory, `localStorage`, or HTTP headers.

### Recommendations for Auth2C itself

The Auth2C hosted pages should add CSP headers to mitigate XSS on the account UI. The inline scripts in `pages.ts` would need to be refactored to use nonces or moved to external script files to comply with a strict CSP. This is not yet implemented.

## Decoded vs. verified claims

The browser SDK decodes the JWT payload client-side (base64 decode of the middle segment) and exposes `userId`, `email`, `name`, `picture`, and `expiresAt` as display fields. These decoded claims are **not cryptographically verified** and must not be used for authorization decisions.

For server-side verification, relying parties should:

1. Fetch JWKS from `https://auth.example.com/.well-known/jwks.json`.
2. Verify the ES256 signature, issuer (`iss`), audience (`aud` = `origin:<your-origin>`), and expiration.
3. Optionally call `/session/check` to confirm the session is still active (not revoked).

## Live revocation limitations

- Self-contained bearer tokens cannot be cryptographically "unissued." Once signed, the JWT is valid until it expires or the session is revoked.
- **Local verification** (checking signature, issuer, audience, expiration) proves only that the token was issued by Auth2C and has not expired. It does **not** detect revocation.
- **Immediate revocation** requires calling `/session/check` server-side. Auth2C enforces revocation at the session row level — a revoked session's token is rejected immediately, even if the JWT has not expired.
- The `/session/revoke` endpoint revokes only the specific session identified by the token's `jti`. Other sessions for the same user/origin remain active.
- Grant revocation (`/account/grants/revoke`) revokes the grant and all active sessions for one origin in a single D1 batch.

## Logging rules

Auth2C does not log bearer tokens, authorization codes, PKCE verifiers, or Google ID tokens. The Worker code contains no logging statements. Cloudflare's standard Workers Analytics and Logs may capture request metadata (URLs, response status codes) but not request bodies or authorization headers at the default configuration level.

Operators should ensure that any Cloudflare Logpush or Real-time Logs configurations exclude the `Authorization` header and `/token` request bodies.
